Agent memory under token budgets

16 Sep 2026 Stub

Long-running agents need memory that survives the request. They also have a context window. Those two facts fight if you treat memory as "paste everything." The service I built keeps hierarchical memory per tenant, then hydrates a ranked slice that fits a budget.

Semantic ranking is how you pick the slice. Evidence tracking is how you know why an item was included. Promotion workflows are how a working note becomes longer-lived memory instead of sitting in a scratch layer forever. Stores are pluggable so the API does not assume one database.

This stub is the constraint, not the retrieval cookbook. See the agent memory project page for FastAPI, PostgreSQL, vector search, and ECS. I will add packing rules and failure cases here when I write them down properly. No recall percentages on this page.
